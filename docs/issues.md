# Known issues

This doc outlines some known issues that we either work around or should fix at some point

### Long Tail p99 queries

We currently have quite a large diff between our p50 queries (~10ms) and our p99 queries (can be multiple seconds). It's still not obvious why our p99 queries are so long as they usually are normal queries with fast p50. The hunch is that there's some level of connection saturation happening causing the p99 queries to wait for a postgres connection. We use PgBouncer.

It's not obvious how we get into situations where there are enough long queries to cause queuing. Need more investigation. Note that we do have statement timeouts configured at the DB level as well. We have quite a bit of monitoring set up around our query timing + DB connection pooling and saturation metrics.

### Substream staleness

In the past we've encountered a had situations where our substreams RPC becomes stale and we don't receive any new blocks. Each time we've had to reach out to Pinax to investigate on their end. This has happened twice but not in the last few weeks (March 2026).

### Postgraphile API vs Custom GraphQL API vs REST API

We currently use a mix of Postgraphile and REST endpoints. Our data model is quite hard to write performant GraphQL resolvers for due to the graph-based N+1 nature of the data model. Additionally, there are queries we require for products which have no equivalent Postgraphile resolver. For these queries we've written custom REST APIs.

We should consider making the Postgraphile API legacy in favor of more custom tooling for our products, both for consumer app ergonomics AND API performance.

### Proposal ID collisions

Proposal IDs are generated by clients before publishing the proposal onchain. Proposals are also updateable. We should make sure we're guarding against malicious proposal hijacking if someone publishes a proposal using an existing proposal ID.
